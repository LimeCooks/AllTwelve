# Film playback and removal

The owner clarified the failure: desktop playback and pause worked, but seeking did not, and film deletion was not discoverable. The old Film Room slider had a controlled value derived from a clip start and no change handler. Playback was also gated by canplay, and the video stayed hidden before that event.

Film Room now displays native video controls for seeking, playback, volume and fullscreen, with playsInline and metadata preload. The separate strip only jumps between charted clips; it no longer duplicates the video controls. There is no canplay gate to pressing Play. Clip jumps wait for metadata when needed and safely bound their requested start. Native media errors have an explicit retry action. Existing private byte-range serving is unchanged.

A visible Delete film action fetches a fresh, named confirmation including the saved clip count. The version covers raw film fields and clip content, including notes. Before deletion is marked, an atomic database assertion verifies all those fields again; numeric clip times are compared as SQL values rather than formatting-sensitive JSON text. Stale confirmations are blocked and offer Reload library. The target ID/version stay frozen while the dialog is open. Unsaved clip edits are discarded only after an explicit delete or reload decision.

Removal marks the asset deleting, removes owned uploaded bytes when no other active film references them, then deletes the record and cascading charted clips. Storage or final database failure leaves the record as a durable retry marker. Pending film records cannot accept clip edits, metadata saves or re-registration. A pending shared reference does not retain a file when every reference is already being deleted. There is no in-product undo; existing external backups are not erased by this action. No hosted owner recording was deleted during implementation or QA.

Validation: real handler/SQLite tests cover stale and late clip edits, identity and owner isolation, file-removal failure/retry, database failure after file removal, shared-file retention and pending shared cleanup. Local browser QA used an actual disposable saved MP4: the native timeline moved currentTime from zero to about 3.02 seconds while paused, playback resumed after seeking, reverse seek returned to zero, and a charted clip jump sought to one second. A new clip added after opening Delete blocked removal and remained intact. Desktop and 390px phone layouts were inspected. The disposable recording, clip and uploaded bytes were then removed through the API; the original local film payload matched its baseline. The release rehearsal additionally checks real packaged worker storage upload/register/chart, stale deletion rejection and full file removal before rollback/forward checks. Its storage fixture is not presented as a playable video.

Limits: physical Safari/Firefox rechecking with the owner's recording remains a handoff check; native controls do not transcode unsupported video formats. The upload limit remains 250 MB. A register request racing a final removal for an identical storage key needs a broader per-file coordination design; regular uploads use fresh UUID keys. Related saved report/gameplan source references can become unavailable after intentional deletion. This does not add an automatic backup schedule or global trash/restore.

Implementation references: [HTML video controls](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/video), [media currentTime](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/currentTime), [WebKit media policies](https://webkit.org/blog/6784/).

## Film load and save integrity

Film Room validates complete library responses before applying them. Switching requests cancel older reads and ignore late responses; Retry targets the film that failed to open. A failed read preserves the current film and draft, and an initial failed read cannot be edited as an empty library. Storage upload and registration share the mutation lock, preventing overlapping clip edits or film operations during upload.

New clip saves use a stable client UUID until success, and the response names the exact saved clip ID. Retrying a failed new save therefore targets the same record; selecting a saved clip no longer assumes the last clip in the response is the one saved. Explicit new-ID creation validates UUIDs and still enforces team/film ownership. Starting a new clip or discarding a draft resets uncontrolled stat fields with a fresh form key. This does not add optimistic concurrency for two people editing the same existing clip.

Validation: 62 tests pass, including real SQLite/handler coverage for saving and retrying a clip whose ID is not last in the response, invalid/mixed responses, request cancellation and error handling. Local browser QA confirmed that an invalid time range preserves notes and input, correcting it saves the exact clip, New clip clears saved fields, Keep editing preserves a dirty draft, and Discard and continue loads the other film's own saved note. Both disposable films and their uploaded bytes were removed, and the original local library matched its baseline exactly. Upload locking and late-response handling have contract/code verification; a delayed-network browser upload was not exercised.

Creation retry safety: `create: true` is now a replay-only operation when its ID already exists in the selected film. The server compares all stored clip fields with the requested creation payload, returns the existing saved ID only when they match, and rejects differing details with 409 without executing an update. This prevents a lost creation response retried after a later clip edit from overwriting that edit. Normal existing-clip edits explicitly use `create: false`. The real-handler test verifies an unchanged creation replay, a later explicit edit, rejection of the stale creation retry, and preservation of the later saved note. This is not a persistent creation ledger: retrying a creation after the record was intentionally deleted can recreate it, and concurrent ordinary edits still need revision protection.
